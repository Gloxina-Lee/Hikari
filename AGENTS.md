# Sakurairo repository guidance

## Project intent

- This is an independent, heavily customized fork of the Sakurairo WordPress
  theme. Do not assume that compatibility with the official upstream repository
  is required, and do not add or change Git remotes unless the user asks.
- The repository intentionally combines the PHP WordPress theme and the former
  `Sakurairo_Scripts` front-end source tree.
- The automatic theme updater and version telemetry have been removed. The fork
  rejects upstream theme update entries and cleans legacy updater schedules and
  state once after deployment.
- Read [MODELS.md](MODELS.md) as the project module map and navigation aid. Treat
  the source code as authoritative if that document becomes stale. Do not rewrite
  `MODELS.md` unless the user asks.

## Repository layout

- The repository root is the installable WordPress theme. PHP templates,
  `functions.php`, `style.css`, `inc/`, `opt/`, and the runtime `js/` assets live
  here.
- `scripts/` contains editable front-end JavaScript, TypeScript, and style source,
  plus its own `package.json` and lockfile.
- `scripts/dist/` is generated by webpack and is ignored by Git.
- `js/` is the asset directory actually consumed by the WordPress theme. A build
  does not update it automatically.
- `scripts/sync-dist.mjs` compares or safely replaces `js/` with `scripts/dist/`.
- `.wp-env.json` defines the local Docker WordPress environment.
- `DEVELOPMENT.md` is the human-facing setup and command reference.

## Local environment

- Expected host setup: Windows with Docker Desktop using WSL 2, Node.js 24 LTS,
  and pnpm 11.19.0.
- Run commands from the repository root unless a command says otherwise.
- `wp-env` runs only the development environment. The tests environment is
  disabled because it is not needed for normal theme work.
- The local site is `http://localhost:8088`; `8888` is inside a Windows-reserved
  port range on the current workstation.
- Default local credentials are `admin` / `password`.
- `.wp-env.json` follows the latest stable WordPress and its default PHP image.
  Do not assume the observed versions are permanent; query them when compatibility
  matters.

## Common commands

```powershell
pnpm install --frozen-lockfile
pnpm frontend:install
pnpm wp:start
pnpm wp:status
pnpm wp:logs
pnpm wp:stop
```

Front-end workflow:

```powershell
pnpm frontend:build
pnpm frontend:watch
pnpm assets:check
```

- `pnpm frontend:build` creates a production build in `scripts/dist/`.
- `pnpm frontend:watch` creates development output and must not be used as release
  assets without a subsequent production build.
- `pnpm assets:check` exits with status 1 when `scripts/dist/` and `js/` differ;
  that exit status is an expected difference signal, not necessarily a broken
  build.
- `pnpm assets:deploy` atomically replaces the theme's entire `js/` directory.
  Do not run it unless the user explicitly authorizes deploying generated assets.

## Validation expectations

- Preserve unrelated working-tree changes and inspect `git status` before broad
  edits. Never restore deleted files merely because they appear in Git status.
- For front-end changes, run `pnpm frontend:build`, then
  `pnpm assets:check`. Report webpack warnings separately from build failures.
- For PHP changes, lint all affected PHP files. For broad changes, lint the whole
  theme inside the wp-env PHP container.
- For runtime changes, ensure wp-env is running, confirm the active theme is
  `Sakurairo`, request both `/` and `/wp-admin/`, and inspect WordPress debug logs.
- Do not silently update dependency versions or lockfiles. Keep frozen-lockfile
  installs reproducible unless dependency maintenance is the requested task.

## Known baseline behavior

- The merged front-end source builds successfully. At the time this file was
  written, `scripts/dist/` and the committed `js/` directory intentionally differ;
  no generated assets have been deployed.
- A fresh-theme activation produced one initial fatal error at `footer.php:111`
  because `reception_background` was null. After theme options initialized,
  repeated home-page smoke tests completed normally. Treat this as an existing
  fresh-install edge case until it is fixed deliberately.
- Current requests can log WordPress notices about enqueuing block styles too
  early, followed by a headers-already-sent warning at `header.php:44`.
- The Bilibili favourites integration can log a folder-fetch failure when it is
  not configured.
- The theme's `php_notice_filter` handling can override `WP_DEBUG_DISPLAY`, so
  inspect both rendered output and `debug.log` during testing.

## Scope and safety

- Do not remove the updater or another major module merely because it is listed as
  planned work; wait for an explicit implementation request.
- Do not overwrite `js/`, reset the WordPress database, or run destructive Git
  commands without explicit authorization.
- Keep environment/tooling changes separate from theme behavior fixes where
  practical, and clearly report existing compatibility warnings rather than
  hiding them through local configuration.
